# Deploy the Hosted Foundry agent

This folder deploys the LangGraph application code as a Microsoft Foundry
Hosted Agent. It is a separate deployment from the repository
[quickstart](../README.md#deploy-in-six-steps-four-commands).

- The root quickstart creates the Azure AI Search knowledge environment, the
  Foundry account and project, model deployments, Search connection, synthetic
  corpus, custom skill, monitoring, identities, and RBAC.
- This folder packages and publishes the agent code in
  [`main.py`](./main.py). Its [`azure.yaml`](./azure.yaml) contains
  `codeConfiguration`, so `azd deploy` performs direct code deployment.
  Docker and Azure Container Registry are not required.

Do not run `azd provision` for this flow. The root quickstart already created
the Foundry project and the agent is bound to that existing project.

## SharePoint document permission trimming

This hosted agent already uses Toolbox integration that forwards the
request-scoped Foundry caller context. The Toolbox bridge below creates its
knowledge-base MCP connection with `user-entra-token` and the
`https://search.azure.com` audience, so Search can evaluate the signed-in user
instead of a shared application identity.

To use that path, first complete
[SharePoint group-based document permission trimming](../docs/sharepoint-permission-trimming.md).
The SharePoint source must ingest `groupIds`, its generated index must enable
the matching permission filter, and each hosted user must have the required
Foundry access and complete any prompted consent. Do not change the Toolbox
connection to shared credentials or service-identity authentication when
per-user trimming is required.

## Prerequisites

1. Complete and verify the root [quickstart contract](../docs/quickstart.md).
   Keep the ignored
   `.azure/quickstart-contract-<deployment-id>.json` file generated by that
   deployment.
2. Install Azure CLI and Azure Developer CLI (`azd`). Authenticate both
   yourself before continuing. This guide does not run a login command for you.
3. Install the `azure.ai.agents` azd extension required by
   [`azure.yaml`](./azure.yaml).
4. Have permission to read the quickstart resources, manage Foundry project
   connections and Toolboxes, and deploy Hosted Agent code.
5. Create the Toolbox bridge below before deploying the agent. The script
   replaces the named Toolbox and its `dispute-kb-mcp-conn` connection, so
   review the selected project and Toolbox name before authorizing
   `-ReplaceToolbox`.

## Use azd without persisting the user-agent setting

Run the remaining commands in PowerShell. Define this wrapper once per shell:

```powershell
function Invoke-FoundryAzd {
  $previous = $env:AZURE_DEV_USER_AGENT
  try {
    $env:AZURE_DEV_USER_AGENT = 'microsoft_foundry_skill'
    & azd @args
    if ($LASTEXITCODE -ne 0) {
      throw "azd failed with exit code $LASTEXITCODE."
    }
  }
  finally {
    $env:AZURE_DEV_USER_AGENT = $previous
  }
}
```

Every `Invoke-FoundryAzd` call below sets
`AZURE_DEV_USER_AGENT=microsoft_foundry_skill` only for that invocation and
restores the prior process value. It never writes the setting to an azd
environment, repository file, or user profile.

If the hosted-agent extension is missing, install it after reviewing the
extension requirement:

```powershell
Invoke-FoundryAzd extension install azure.ai.agents
```

## Create the public Toolbox bridge

Run this example from the repository root. Replace only the deployment ID and
choose the Toolbox name that the hosted agent should use.

```powershell
$deploymentId = '<deployment-id>'
$toolboxName = '<chosen-toolbox-name>'
$contractPath = Resolve-Path ".\.azure\quickstart-contract-$deploymentId.json"
$contract = Get-Content -LiteralPath $contractPath -Raw |
  ConvertFrom-Json -Depth 100

if ($contract.schemaVersion -ne '3.1.0') {
  throw "Unsupported quickstart contract schema: $($contract.schemaVersion)"
}

$environment = "$($contract.deployment.environment)"
$requiredContractValues = @{
  AZURE_SUBSCRIPTION_ID = "$($contract.deployment.subscriptionId)"
  AZURE_RESOURCE_GROUP = "$($contract.deployment.resourceGroupName)"
  AZURE_SEARCH_SERVICE = "$($contract.resources.search.name)"
  AZURE_SEARCH_ENDPOINT = "$($contract.resources.search.endpoint)"
  FOUNDRY_ACCOUNT_NAME = "$($contract.resources.foundry.accountName)"
  FOUNDRY_PROJECT_NAME = "$($contract.resources.foundry.projectName)"
  FOUNDRY_PROJECT_ENDPOINT = "$($contract.resources.foundry.projectEndpoint)"
  FOUNDRY_TOOLBOX_NAME = $toolboxName
  FOUNDRY_KB_NAME = 'policy-knowledge-base-v2'
  AISEARCH_CONNECTION_NAME = "search-$environment"
}

$missing = @($requiredContractValues.GetEnumerator() | Where-Object {
  $null -eq $_.Value -or "$($_.Value)".Trim().Length -eq 0
} | ForEach-Object Key)
if ($missing.Count -gt 0) {
  throw "The quickstart contract or chosen Toolbox name is missing: $($missing -join ', ')"
}

foreach ($entry in $requiredContractValues.GetEnumerator()) {
  Set-Item -Path "Env:$($entry.Key)" -Value "$($entry.Value)"
}

$previous = $env:AZURE_DEV_USER_AGENT
try {
  $env:AZURE_DEV_USER_AGENT = 'microsoft_foundry_skill'
  & .\scripts\maintenance\04-rewire-toolbox.ps1 -ReplaceToolbox
}
finally {
  $env:AZURE_DEV_USER_AGENT = $previous
}
```

The subscription, resource group, Search service and endpoint, and Foundry
account/project values come directly from the contract. The contract records
the quickstart environment but not the logical knowledge-base and Search
connection names. Those are deterministic Bicep names:
`policy-knowledge-base-v2` and `search-<environment>`, respectively, as defined in
[`infra/main.bicep`](../infra/main.bicep).

The script uses the process environment when `-ConfigPath` is omitted. For
automation that already maintains a public, non-secret config file, pass that
exact file with `-ConfigPath`; the script never falls back to `config/demo.env`
or another private repository path.

## Bind an azd environment to the existing project

Continue in the same PowerShell session so `$contract` and `$toolboxName` remain
available, then enter this folder:

```powershell
Set-Location .\langgraph-agent-hosted-foundry
$azdEnvironment = '<azd-environment-name>'
```

For a new local azd environment:

```powershell
Invoke-FoundryAzd env new $azdEnvironment `
  --subscription $contract.deployment.subscriptionId `
  --location $contract.deployment.location `
  --no-prompt
```

For an azd environment that already exists, select it instead:

```powershell
Invoke-FoundryAzd env select $azdEnvironment --no-prompt
```

Set all existing-project values. `TOOLBOX_NAME` must match the Toolbox created
above.

```powershell
Invoke-FoundryAzd env set `
  "AZURE_SUBSCRIPTION_ID=$($contract.deployment.subscriptionId)" `
  "AZURE_LOCATION=$($contract.deployment.location)" `
  "AZURE_RESOURCE_GROUP=$($contract.deployment.resourceGroupName)" `
  "AZURE_AI_PROJECT_ENDPOINT=$($contract.resources.foundry.projectEndpoint)" `
  "FOUNDRY_PROJECT_ENDPOINT=$($contract.resources.foundry.projectEndpoint)" `
  "AZURE_AI_PROJECT_ID=$($contract.resources.foundry.projectId)" `
  "AZURE_AI_MODEL_DEPLOYMENT_NAME=$($contract.resources.foundry.chatDeploymentName)" `
  "TOOLBOX_NAME=$toolboxName"
```

Inspect the resolved values and project binding before deployment:

```powershell
Invoke-FoundryAzd env get-values
Invoke-FoundryAzd ai project show --output json
Invoke-FoundryAzd ai agent show --output json
```

Before the first deployment, agent status can be `not_deployed`. The project
endpoint and project ID must resolve to the quickstart project. Do not run
`azd provision`.

## Deploy and verify

Deploy the code directly:

```powershell
Invoke-FoundryAzd deploy --no-prompt
Invoke-FoundryAzd ai agent show --output json
```

A successful status response reports an active or deployed version and its
Responses protocol endpoint.

The following remote smoke invocation is **optional and billable** because it
can start hosted compute and consume model tokens. Run it once only when you
want to verify the deployed endpoint:

```powershell
Invoke-FoundryAzd ai agent invoke --new-session `
  'Summarize the evidence needed for a synthetic duplicate-dispute review.'
```

## Redeployments and versions

Each successful `azd deploy --no-prompt` publishes an immutable Hosted Agent
version. After a code or configuration change, rerun the deploy command and
then inspect `azd ai agent show --output json` to confirm which version is
active. An identical build can report that the existing version is already
active and skip polling.

## Troubleshooting

- **Wrong azd environment:** run `env select`, then inspect `env get-values`.
  Do not deploy until subscription, resource group, endpoint, project ID,
  model deployment, and Toolbox name all refer to the same quickstart
  contract.
- **Wrong project binding:** compare `ai project show --output json` with
  `contract.resources.foundry.projectEndpoint` and
  `contract.resources.foundry.projectId`. Reset the azd environment values;
  do not provision another project.
- **Model not found or HTTP 404:** verify
  `AZURE_AI_MODEL_DEPLOYMENT_NAME` equals
  `contract.resources.foundry.chatDeploymentName`, and verify the project
  endpoint is the contract endpoint.
- **Toolbox not found:** verify `TOOLBOX_NAME` exactly matches
  `FOUNDRY_TOOLBOX_NAME` used by the bridge script and that the script targeted
  the same project.
- **Authorization failure:** authenticate `az` and `azd` yourself in the
  current shell and confirm you have project, connection, Toolbox, deployment,
  Search-read, and role-assignment-read permissions required by the bridge
  preflight.
- **Docker or ACR prompt:** stop and inspect [`azure.yaml`](./azure.yaml).
  `codeConfiguration` should remain present; this guide uses direct code
  deployment.
